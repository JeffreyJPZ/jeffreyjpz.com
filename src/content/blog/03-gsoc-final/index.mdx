## Project deep dive

If you haven't already, I highly recommend that you read the [intro blog post](https://jeffreyjpz.com/blog/01-gsoc-intro/) and [midterm blog post](https://jeffreyjpz.com/blog/02-gsoc-midterm/)

### Background context

Interacting with "pure" LLMs is almost never done anymore — familiar tools like the web versions of Claude and ChatGPT have shifted to "conversational agents",
with memory to remember previous messages and tool calling to enrich themselves with relevant information.
Conversational agents are the most visible kind of agent to consumers today, with use cases such as search queries, customer support, or troubleshooting.

However, what companies really want is to build autonomous agentic **systems** that can **proactively** execute business-critical processes and replace your job.
For this to happen, agents must be able to run in the background (because nobody wants to babysit 24/7), run for a long time (since a lot of business process are complex), escalate when necessary, among others.
On top of that, while running autonomous agents in production, more issues pop up:
- Agents are bursty — they may execute for several minutes before waiting for approval for multiple days or weeks
- Failures are common — when agents restart, they repeat LLM/tool calls, which can be expensive at scale
- Governance and compliance — in highly-regulated industries, you need to be able to tightly control what an agent can access, and prove what an agent did at each step (and who authorized it)
- Connecting to existing data sources and triggering agents from them involves tons of boilerplate code, reducing developer velocity

Fortunately for them (and unfortunately for us), there are several CNCF projects in this space:

[Drasi](https://drasi.io/) is a CNCF Sandbox project aimed at making detecting and reacting to changes across data sources easier via declarative configuration. It consists of three main components:
- **Sources** to ingest data from existing systems.
- **Continuous Queries** that evaluate incoming data from different sources against user-defined, high-level "business conditions", and emit "change" events when those conditions are satisfied.
- **Reactions** to push events to downstream consumers.

[Dapr](https://dapr.io/) is a CNCF Graduated project consisting of a sidecar runtime and multiple APIs to help developers build microservices and distributed systems.
One of its most popular and useful features is its built-in durable workflow engine (based on virtual actors),
which powers the [Dapr Agents](https://docs.dapr.io/developing-ai/dapr-agents/dapr-agents-introduction/) agentic framework/subproject.
Dapr Agents comes with [many advantages over traditional agentic frameworks](https://docs.dapr.io/developing-ai/dapr-agents/dapr-agents-why/),
but the one I find personally interesting is that agents can be deactivated when idle and reactivated on demand,
allowing many agents can be multiplexed onto a single core (all thanks to the virtual actor architecture). There's nothing quite like it today, but I digress.

As mentioned in the summary, this GSoC project was focused on integrating the two projects to enable new use cases,
requiring a lot of exploratory work and uncovering gaps in both projects along the way. The following sections discuss
the work that was done and the challenges faced along the way.

### Static Drasi subscriptions and initial Drasi extension

After familiarizing myself with both projects' architectures and learning about Kubernetes during the community bonding period,
we decided that the first milestone should involve writing an extension for Dapr Agents that can trigger agents with events assuming the types of events (i.e. Drasi queries) are known in advance.
While not ideal, this would help us discover any initial gaps and scope the work for the GSoC period appropriately.

Initially, we were thinking of a decorator `@drasi_trigger` allowing us to attach metadata (Drasi query ID, Dapr pub/sub component name, pub/sub topic name, etc.)
to the agent, and later use that metadata at runtime to create Dapr pub/sub subscriptions and filter on events as they arrive.
However, looking at the agent initialization flow, there was no easy way to place the decorator as all flows boiled down to something like:

```python
agent = DurableAgent(...)

runner = AgentRunner()
try:
  runner.serve(agent)
finally:
  runner.shutdown(agent)
```

Because of this, we instead pivoted to lifecycle hooks (see this [PR](https://github.com/dapr/dapr-agents/pull/638)) so that we could have a callback to modify the agent
**after** initialization and **before** it is hosted as a service (i.e. the blocking `serve()` call). This way, we could not only preserve the existing agent code and initialization flow,
but we could also leverage some of the existing subscription creation code.
As a result, anyone using our extension wouldn't have to learn a new paradigm as the initialization flow looked like:

```python
agent = DurableAgent(...)

drasi_trigger(
  agent,
  query_id="at-risk-orders-query",
  pubsub="pubsub",
  topic="orders.at-risk",
)

runner = AgentRunner()
try:
  runner.serve(agent)
finally:
  runner.shutdown(agent)
```

While building out an end-to-end example, we had to make a decision: what would the event shapes be?
Since we were reusing an existing [Drasi "pub/sub router" reaction](https://drasi.io/drasi-kubernetes/how-to-guides/configure-reactions/configure-post-pubsub-reaction/#output-formats),
the choice was between "packed" events representing multiple batched changes, "unpacked" events representing a single, discrete change, or both.

To minimize scope creep, we focused on unpacked events for two reasons:
1. Agents would have an easier time acting on individual changes.
2. Common issues relating to multi-tenant architectures would be eliminated off the bat — data leakage, the "noisy neighbour" problem where one slow course of action blocks the others from completing, among others.

As a concrete example, imagine that you have an agent that is triggered when orders are delayed/at-risk and proactively resolves them.
A packed event could contain multiple at-risk order records, each associated with a customer who holds a certain subscription tier.
Premium subscription tiers would have different guarantees than basic subscription tiers,
meaning that an agent would need to delegate to specialized subagents to avoid juggling many tasks (which still suffers from data leakage and the noisy neighbour problem without careful design).
You might also have a custom enterprise tier for enterprise customers with different SLAs, which could force you to use unpacked events anyway.

Now that we could receive events, the next step was to be able to filter, validate, and transform them into a actionable task message before triggering the agent.
Even before the GSoC period, I'd recognized that this would be a problem — Dapr's [content-based routing](https://docs.dapr.io/developing-applications/building-blocks/pubsub/howto-route-messages/),
is done by the Dapr sidecar for push-based subscriptions, but Dapr Agents recently migrated to pull-based subscriptions (probably for natural backpressure). This grunt work then had to be done in client code,
but there was no support for it at the time. I opened an [issue for client-side filtering](https://github.com/dapr/dapr-agents/issues/561), [reviewed the eventual PR](https://github.com/dapr/dapr-agents/pull/605#pullrequestreview-4392290650),
and eventually [added client-side transformation](https://github.com/dapr/dapr-agents/pull/646) myself.
We also decided that Drasi subscriptions should **not** share the same pub/sub topic used by the agent's primary subscription as there was no way to deliver a single event (i.e. fan-out) to multiple subscription handlers at the application level
(nor should it, it's better suited to the workflow level since our focus is on business processes).
This was a painful realization — I spent many hours trying to debug why Drasi events **sometimes** failed to trigger agents before figuring out that there was a race condition between the primary handler and the Drasi event handler.

After that, the core of the work was done, but we still had another decision to make as to who would own the models used to validate Drasi events.
Since they were autogenerated from JSON schemas on the Drasi side, it was natural to consume them as a part of a Drasi SDK.
Unfortunately, limitations with the autogeneration tool `datamodel-codegen` used by Drasi, as well as model name collisions due to how the JSON schema was defined
(see the entire diagnosis [here](https://github.com/drasi-project/drasi-platform/pull/437#pullrequestreview-4548162065)) forced us to vendor (a fancy term for copy over) the schemas
to the extension, as otherwise we'd be blocked indefinitely trying to devise a clever workaround.

After [tackling another race condition](https://github.com/dapr/dapr-agents/blob/9fc673fee96057153ff163b690be9cea4c7a823b/ext/dapr-agents-ext-drasi/tests/test_drasi_trigger.py#L104-L110) where tests would complete before agents could be scheduled to run,
the initial extension was able to be [merged](https://github.com/dapr/dapr-agents/pull/665) and [released](https://pypi.org/project/dapr-agents-ext-drasi/).

### Exploring dynamic Drasi subscriptions

The second milestone for the GSoC period explored the idea of agents discovering Drasi queries at runtime, subscribing to them, then waiting for events to arrive and acting on them with dynamic, LLM-generated, context-specific "instructions".
The main benefit of this would be that agents and Drasi pipelines can be developed independently, and not having to redeploy agent apps when Drasi queries are updated.
In addition, the agent would be able to "remind" itself about what to do with its generated "instructions", which is useful for long-running tasks. 

As this part of the project involved multiple services across different namespaces, we made sure to write a [design document](https://docs.google.com/document/d/1H1DxIRP-7Duc0njXhe5EKXnx1Ztd5jIuyUUIKVp7qU4/edit?usp=sharing)
with the decisions and tradeoffs made. However, I'll summarize the most interesting challenges here.

After some discussion, we agreed that a dedicated Drasi reaction/connector for routing events to agents (an "agent router") was necessary,
as the pub/sub router used in the previous milestone relied on declarative configuration (YAML) and had no concept of agent identity or support for agents.
To allow the agent to subscribe, there needed to be an [MCP](https://modelcontextprotocol.io/docs/2026-07-28/getting-started/intro) server with tools, which we decided would be in-process as the tools would be specific to this reaction (and for simplicity).

We also needed to maintain some sort of subscription state in the reaction, as some agents may want only certain types of events for certain queries, yet we didn't want agent developers to write one-off logic to filter out events.
However, a simple in-memory store wouldn't be enough for anything outside of local development or testing, so this needed to be backed by a durable store
(we chose [Dapr state stores](https://docs.dapr.io/operations/components/setup-state-store/) as Drasi already relied on Dapr and to enable developers to swap in their preferred storage provider).
One downside of this choice is that we can only support one replica without implementing some sort of cache invalidation, but that was a problem we figured we could deal with later down the line (hopefully).

The state model itself was influenced heavily by Dapr state store limitations — being a generic abstraction, it only supports key-value patterns.
On top of that, when an event was emitted, we had to be able to look up all of the agents interested in that event with just the event itself and its metadata.
While there are definitely some optimizations to be made (potentially using sorted lists), we ended up with a sort of "nested" map:

```json
{
  "query_id_1": {
    "subscription_id_1": {...},
    "subscription_id_2": {...},
    "subscription_id_3": {...},
    ...
  },
  ...
}
```

Next, we had to deal with fundamental distributed systems problems: delivery guarantees, consistency, and caching.
We prioritized guaranteed delivery and strong consistency throughout for several reasons:
1. Agents would be executing in the background — extra latency is not a problem since nobody is actively monitoring them.
2. Our focus was on autonomous agents executing not just grunt work, but critical and/or customer-impacting business processes.
Imagine what would happen if your agent never kicked off a critical action because an event was dropped due to network congestion, or failed to even be sent because a replica had stale subscriptions?
2. The nature of the projects — Dapr Agents is designed for enterprise scale, while Drasi solves a specific problem for enterprises that want to act on changes across multiple, scattered data sources.

With guaranteed delivery, we needed to be able to handle duplicate messages/actions.
On the reaction side, we made our subscription tool calls idempotent by treating subscriptions as "upserts" and having the agent pass in subscription identifiers.
On the agent side, we wanted exactly-once semantics as otherwise we'd have duplicate events triggering duplicate workflows.
Fortunately, Dapr Agents offered [built-in deduplication in a 60 second window](https://github.com/dapr/dapr-agents/blob/34155c75c36e05285b02ff78e7ded14ef2acf350/dapr_agents/workflow/utils/subscription.py#L61-L79),
which was good enough for us.

For consistency and caching, we decided on a [cache-aside](https://www.geeksforgeeks.org/system-design/cache-aside-pattern/) strategy for reads and a [write-through](https://www.geeksforgeeks.org/computer-organization-architecture/write-through-and-write-back-in-cache/) strategy for writes to provide a balance between simplicity, read performance, and (local) consistency.
We treated the backing store as the "source of truth", ensuring that a subscription can never be lost by writing them to the backing store first before updating the in-memory cache.
Under the assumption that subscription writes would be quite rare, we opted for [optimistic concurrency control](https://en.wikipedia.org/wiki/Optimistic_concurrency_control) with [Dapr's support for ETags](https://docs.dapr.io/developing-applications/building-blocks/state-management/state-management-overview/#why-dapr-chooses-optimistic-concurrency-control-occ)

Once we addressed the problems around the agent router, we needed to figure out the responsibilities of the agent and the agent runtime.
Some of these challenges are extremely interesting as they were unique to our situation (from a non-biased perspective).

The first problem relates to subscriptions — we've already ensured that subscriptions can never be lost once recorded, but how do we ensure that a subscription request gets delivered?
This is where the agent runtime comes into play, as Dapr's MCP client has retries built-in.

The second problem relates to data consistency across services. For example, say the agent decides to subscribe and fires off a tool call to the agent router, which successfully persists the subscription and sends a response.
If that response **is lost** for whatever reason, there is a window where the agent router could forward an event to the agent without the agent having any record of the subscription (as it hasn't retried and received a successful response),
resulting in this "indeterminate" state. To address this, we implemented a "two-stage" subscription — the agent runtime would persist its own subscription record with a `"PENDING"` status before calling the subscription tool.
Any event that arrived after that point would be handled as there would be a subscription record, and the runtime would mark the subscription as `"ACTIVE"` on a successful response.
This also explains why subscription ID is a client-side concern (which is atypical).

A third problem we faced was that subscription ID and agent ID are **runtime concerns**, and the LLM should **not** be responsible for generating those (for good reasons).
However, the agent router must obtain them somehow, so we needed a way to "inject" these into MCP tool calls without exposing them to the LLM.

Aside — if you aren't familiar with MCP, it's effectively a protocol that standardizes the way agents call APIs.
Most use cases follow the request-response model, where requests and responses are structured JSON that LLMs are all familiar with.
MCP tools are functions that are roughly equivalent to your API routes in a typical web server, but instead of being identified by a path,
tools are identified by tool names (which are part of a **tool schema**).

As MCP is continuously evolving, best practices have not been established yet for injecting runtime arguments.
[Some MCP servers](https://modelcontextprotocol.io/specification/2025-06-18/basic#_meta) accept a `_meta` property that serves a similar purpose as HTTP headers at the connection level,
but we opted to keep our injected arguments (subscription ID, agent ID) at the top level.

Another problem dealt with "reminding" the agent when the Drasi event is received via dynamic, LLM-generated instructions.
Our thought process going in was effectively: ***"When the LLM decides to subscribe, it should be able to determine what it should do to act on an incoming event. Can't we just have instructions as a regular MCP tool parameter with a detailed-enough description?"***
This sounded reasonable enough at the time (apart from the meta prompting required), but we quickly realized that instructions was a agent-only concern and should not be sent as part of the tool call.
Accounting for injected arguments, this meant that we had to maintain **two** different schemas for our subscription tool:

```
LLM-exposed tool schema: { query ID, event types, instructions }
Agent router tool schema: { query ID, event types, agent ID, subscription ID }
```

Once we knew how to generate the instructions, we had to consider the best place to store and inject those instructions.
A natural direction was to leverage the system prompt/instructions, since Dapr Agents already supported "hot-reloading" for it (allowing changes to be made at runtime with zero downtime), but this was discarded.
To understand why this was insufficient, we need to look at how Dapr agents are deployed. In our case, a pod holds an agent app, or "worker host" that can host many logical agents (instances) for a given type
(if you're interested, you can read up on how the Dapr workflow substrate scales [here](https://docs.dapr.io/developing-applications/building-blocks/workflow/workflow-architecture/#workflow-scalability)).
Modifying the instructions would affect **every agent belonging to that type**, so it was decided that instructions would be a part of the runtime subscription state.

For instruction injection, we relied on our initial idea of an agent subscribing, "sleep" (deactivate), and "wake up" (reactivate) on events to help guide us.
To "wake up" the agent, we could either route the event to the same agent instance, potentially resulting in "eternal" agents with massive history logs; or we could
continue treating agents as disposable workers since all the information needed to look up subscription state would exist on the event (namely CloudEvent metadata).
We ultimately went with the second approach as no functionality exists in Dapr Agents today to handle the first,
but this is still up in the air (again, there are no best practices to follow).

The exact implementation details can be found in [this PR](https://github.com/dapr/dapr-agents/pull/744),
but I won't delve any further since this blog post is long enough as is.

## What I learned

Here's what I've learned from working on my project and observing how other engineers operate on the Drasi and Dapr projects.
Some of this may be specific to open-source work rather than traditional corporate/product work, but I hope that some of this advice will be useful to students and newcomers to the industry.

- Write down everything — your action items for today, error logs and steps you took while debugging, repeated shell commands. As someone new to the industry, you need to know so much
that your brain simply can't hold it all.
- Do your research — AI is useful in that you don't even need to know the right terminology or write perfectly coherent thoughts. For example, when I was wrestling with Python package management
to be able to publish the Drasi extension as a separate package yet have it as part of a monorepo,
it helped explain to me how module resolution works despite me likely misusing a bunch of terms (unfortunately I've forgotten how it works now).
- Use AI judiciously — this might be partially due to necessity since I couldn't afford to burn through that many credits, but as someone who is relatively inexperienced,
you **should** still take some time to write code by hand as it forces you to slow down and think about design principles, edge case handling, error handling, and other foundation skills.
Reviewing AI-generated code is not the same — even if you scrutinize every line, how do you catch these things without having thought about it or experienced it yourself?
Sure, you could plan for every failure mode, but that again requires experience (unless you're a prodigy). That said, I did leverage it extensively for prototyping and work involving lots of boilerplate (e.g. tests),
as the stakes are much lower there.
- Make life easier for other people — this comes in muliple forms such as communicating frequently (this is usually asynchronous), pointing out questionable areas on PRs, preparing discussion points before meetings, and trying to unblock yourself as much as possible.
With higher productivity expectations nowadays due to AI, people are stretched thin, so removing some of this burden is highly appreciated.
- Senior/staff engineers aren't gods — they will make mistakes, backtrack on earlier decisions once they have more information, and disagree with each other.
What matters is having a breadth of knowledge, depth in a domain or two, and the ability to navigate ambiguity, adapt to changing priorities, and take ownership of high-impact projects, across teams if necessary
(for Drasi and Dapr this is equivalent to working across multiple codebases — core runtime, client libraries/language SDKs, frameworks and integrations).
This means that the dreaded **soft skills** are equal to or arguably more important than technical skills as you need to be able to advocate for yourself and your work, no matter what it is.
- Most importantly, it's ok to not know what you're doing — I'm not exaggerating when I say that I woke up most days not knowing what I needed to do that day because of all of the ambiguity.
This is why it's important to identify your daily/weekly goals, and how they relate to the big picture before you break them down into daily tasks.

## Future work

So far, [v0.1.0 for the Drasi extension has been published](https://pypi.org/project/dapr-agents-ext-drasi/) with the ability to statically subscribe to Drasi queries.
There's also a [very rough proof of concept](https://github.com/drasi-project/drasi-platform/pull/443) of an "agent-aware" Drasi event router with an MCP server. This allows agents to subscribe to Drasi queries dynamically
over any Dapr-supported message broker, and there's [another proof of concept](https://github.com/dapr/dapr-agents/pull/744) demonstrating how Dapr Agents developers can enable this capability with a handful of lines of code.

As school is starting up again, my mentor Aman Singh will pick up from where I left off and create an MVP based on my work, but there are definitely some things that I would like to explore in the future to make things production-ready
(note: this is non-exhaustive):

- Security was out of scope for the GSoC period not only because of time limitations, but because [agent identity](https://www.diagrid.io/blog/agent-identity-on-behalf-of-delegation) is a relatively new problem.
- Scale-to-zero for agent apps (not to be confused with the agents themselves) had to be cut as well due to a lack of Dapr runtime support (you can see some related [proposals](https://github.com/dapr/proposals/pull/77) and [issues](https://github.com/dapr/dapr/issues/10442)).
- Finally, we focused on use cases that could probably be modelled by deterministic workflows (e.g. a basic inventory agent that orders more stock when a product in a database becomes low in stock). Exploring use cases that leverage Drasi's advantages
(detecting high-frequency changes and the absence of change) and Dapr Agents' advantages (adding reliability, scalability, durability, and governance to long-running autonomous agents and orchestrations) could expose interesting gaps.
